Date: 2026-08-28

## Implementation map

### Compact & Resume and ChatGPT SPA lifecycle

Symptoms:

- a new resume tab could wait tens of seconds before sending (see the measurement note below:
  this one is unproven rather than fixed in this pass);
- the composer settings gear could disappear after ChatGPT SPA navigation;
- New Chat could show a meaningless **Compact** pill;
- stale async work must not retarget a continuation after A → B → A navigation.

Design and invariants:

- `extension/content.js::waitForComposer` checks the composer immediately, then observes the DOM
  mount with a bounded 12-second failure deadline. It no longer gates on four repeated
  `document.readyState` samples or a fixed post-insertion wall-clock sleep. The final hydration
  fence is one microtask plus exact normalized composer-text/route/marker checks, and
  `runCommand` runs ahead of status restoration rather than behind it.

  **This state predates this pass.** All four of those properties are present in the published
  2.0.2 tree this line was opened from; no edit in this pass touches the bootstrap send path, and
  the `chatgpt-dom.js` change below is not on it (`CLF_DOM.composer()` resolves `#prompt-textarea`,
  while the new selectors feed only the injected-control anchor). The honest status of the
  tens-of-seconds symptom is therefore **not measured**, in either direction: the structural causes
  it was attributed to are gone from the source, and no before/after wall-clock number was ever
  captured to confirm the user-visible result. Two candidates were checked and ruled out —
  `PORT_TRUST_MS` is a 30-second *cache* that only removes requests, and `HIDDEN_ACTIVITY_MS` is a
  post-startup poll cadence that a fresh marked page reaches only after `runCommand` has already
  run. Closing this properly needs a timed live run, not more source reading.
- So the measurement is now built in rather than left to a future observer. `Command.claimedAt` is
  stamped immediately before the browser is opened and `CommandReceipt.completedAt` when the page
  reports what it did, which spans exactly the user-visible window — Chrome start, ChatGPT load,
  content-script boot, redeem, composer readiness, insertion, Send. `commandLatency()` puts that
  difference into the existing completion log line, so the next real Compact & Resume states its
  own latency instead of leaving it to be re-derived from second-granularity timestamps.
- The composer control is retained and reattached when React replaces its host. Navigation epoch,
  marker and exact conversation checks fence all irreversible sends.
- Real Chrome exposed a second settled New Chat composer shape after sidebar SPA navigation:
  `data-composer-transition-slot="trailing"` with **Start dictation**/**Start Voice**, rather than
  the older transient test-id row. `chatgpt-dom.js` now recognizes that current centralized anchor.
  The regression replaces the complete composer with this exact live shape before reinjection.
- The gear remains present on New Chat because it owns Goal and Auto-compaction settings. Compact
  is unavailable until a real conversation exists, and `renderControl` hides the progress pill for
  `off`/`hidden` states. The reason remains in the gear tooltip and settings sheet.
- One regression drives existing chat → New Chat → chat B → history back/forward → chat A without
  reload and asserts exactly one gear and no stale pill.

Files: `extension/chatgpt-dom.js`, `extension/content.js`, `test/content-script.test.ts`.

### Goal UI, provider boundary and self-healing

Symptoms:

- ordinary user turns briefly painted a speculative Goal loading card;
- unrelated activity repaints rebuilt the Goal editor and reset caret/scroll;
- provider/network/timeout/malformed results could wedge Goal or become user-visible text;
- late/retried results and restarts could duplicate a Goal send or attach it to the wrong chat;
- the stock model changed to GLM 5.3 Flash.

Design and invariants:

- Settling/requesting is visually silent. Only actionable output, a terminal unavailable state or
  an editor the user explicitly opened occupies composer UI.
- Menu rendering has a settings signature; unrelated transcript/activity mutations preserve the
  editor node, unsaved text, focus, selection direction, textarea scroll and sheet scroll.
- `DEFAULT_GOAL_MODEL` is `z-ai/glm-5.3-flash`. Only the exact retired stock default migrates;
  customized model ids are preserved.
- One originating turn/model/context gets at most three attempts. Production delays are 0, 500 and
  1500 ms. Only 408/425/429/5xx, transport failure and timeout are transient, and that is now
  enforced rather than assumed: `goalThrowFailure`/`goalDecisionFailure` classify every outcome,
  and `DETERMINISTIC_GOAL_FAILURES` names the five results a second identical request cannot fix
  (`malformed_completion_response`, `malformed_stream_record`, `reply_too_long`,
  `stream_record_too_long`, `response_body_too_large`). `provider_completion_error` and
  `provider_stream_error` are deliberately *not* in that set: they are the provider reporting its
  own trouble in-body, which is the same class of transient as a 5xx. Attempt generation plus
  `AbortController` suppresses late completions; there is no silent model fallback.
- `draftOpeningMessage` runs that same policy. It previously made exactly one attempt on the
  180 s request timeout, so a saved Goal firing into a brand-new chat could not self-heal from any
  provider hiccup even though this record claimed retries were general. It now uses the bounded
  three-attempt loop with a 30 s per-attempt timeout, which is what makes the total bounded enough
  for a caller to wait on. The extension is the caller, and it was the real ceiling: `call()` in
  `extension/background.js` applied one 10 s `REQUEST_TIMEOUT_MS` to every route, so the browser
  gave up long before the app could retry. `/goal/open` now carries its own
  `GOAL_OPEN_TIMEOUT_MS` (105 s), sized above the app's worst case of three 30 s attempts plus
  backoff.
- HTTP/provider errors, empty/truncated bodies, malformed schema, reasoning/tokenizer leakage and
  internal exception text are failures, never Goal replies. Only a locally validated response or
  stop/`NO_REPLY` decision can cross `humanReply()`.
- Pending/ready/failed drafts cross durable `goal-drafts` state before provider work/publication.
  Browser spent receipts live in both sessionStorage and extension-local storage. Terminal ACK is
  durable, so an app/content-script/MV3 restart or lost ACK response cannot type a success twice.
- Manual Retry names the exact conversation, draft token and client; provider recovery does not
  require toggling Goal off/on. Route/turn epochs prevent an old draft card from appearing in a
  different chat.

Files: `src/main/goal.ts`, `src/main/config.ts`, `src/main/index.ts`, `src/main/bridge.ts`,
`extension/background.js`, `extension/content.js`, `extension/overlay.css`, plus Goal/bridge/
content/extension tests.

### Compact & Resume transaction recovery

The current continuation architecture already models summary request, durable capture, browser
command lease, bootstrap delivery, destination binding and terminal receipt as separate states.
This pass retained and re-ran its crash/duplicate suite rather than replacing it.

Must hold:

- capture/ACK duplicates return the existing handoff/commit;
- no destination conversation id is retryable, not success;
- a failed durable write does not publish the next state;
- app restart restores the exact leased transport without opening another replacement chat;
- session, workspace, Goal and retained worker history move together only after the durable commit;
- old/stale claimants cannot bind the session or retire the original chat.

Primary proof: `test/resume.test.ts`, `test/continuation.test.ts`,
`test/goal-resume-handoff.test.ts`, bridge/content restart and command-receipt cases.

### Tunnel lifecycle

Existing OpenAI Secure MCP Tunnel behavior already supervises `tunnel-client`, uses its completed
poll metric as route proof, distinguishes short network blips from outages, retries an unhealthy/
exited helper with backoff, owns the process tree and fences reports by connection generation.

Concrete gap fixed: Cloudflare quick tunnel reported a helper exit but never restarted it.

`startCloudflared` now:

- owns exactly one child generation;
- clears the old public URL and schedules 2s exponential reconnect up to 60s after exit/start error;
- treats a 45-second no-URL startup as a failed generation, terminates its tree, then retries;
- ignores late URL/error/exit output from a replaced child;
- clears startup/retry timers before Stop and cannot relaunch afterward.

`startOpenAiTunnel` needed the same generation fence, which it did not have. Both of its
supervisor-initiated failure paths did `await stopTree(child); retry(...)`, and `stopTree` makes
that same child emit `exit`, whose listener also calls `retry`. One failed generation therefore
spent two attempts and replaced the 2 s backoff with 4 s. It now carries `generation`/`finished`
like the Cloudflare path: `retry(detail, from, retire?)` refuses a stale or already-answered
generation, and — because arming the replacement before retirement settles could overlap the old
tree with the new one for up to a second — it claims the failure immediately but schedules the
relaunch only after `retire()` resolves. `watch()` re-checks `stopped`/`from === generation` after
every await so an old watch cannot kill a newer generation, and `launch()` re-checks both after
`await fs.rm(healthFile)`, closing a stop-during-launch seam where Disconnect during that await
still spawned a tunnel.

Files: `src/main/tunnel/index.ts`, `test/tunnel-lifecycle.test.ts` (the OpenAI generation tests pin
exactly one replacement per failed generation, its 2 s backoff, and no spawn after a mid-launch
stop); neighboring connection, tunnel-health and bounded-shutdown tests remain authoritative.

### Caller identity and explicit uncaptured authorization

The ordinary proof chain remains request id → extension Fiber evidence → exact conversation
correlation → caller/workspace/terminal owner. Timing, active tab and “only chat” are still never
substitutes.

The new **Uncaptured chat access** switch is off by default and creates one distinct principal,
`authorized:uncaptured`, only after the full exact-evidence wait (when a browser is present).
Captured proof always wins. The principal has a separate workspace key and terminal owner,
`@authorized-uncaptured`; it cannot inherit or poll a captured caller's session. It still passes
live capability, read-only and platform guards.

Disabling it is a revocation, which it previously was not. The switch only stopped
`execCallerOwner` minting the fallback owner for the *next* call, so a background `exec_command`
already owned by `@authorized-uncaptured` kept running under withdrawn authority and the
`authorized:uncaptured` workspace stayed in the map for its full 12 h TTL — meaning a re-enable
inside that window resumed the previous authorisation's learned folder. `settings:save` now calls
`revokeAuthorizedUncaptured()` on the true→false edge: it terminates the sessions that principal
owns, forgets their ownership rows, and clears its workspace. Ownership is forgotten whether or not
termination succeeded, because `execOwnershipDenied` refuses any id it has no entry for — a session
that resisted termination becomes unreachable rather than anonymous and adoptable.

Two races needed explicit fences, both because ownership is published *after* `execCommand`
returns from its initial yield rather than before it:

- a fallback command still inside that yield is invisible to the revoke's registry sweep, and the
  stale call would then publish a live terminal under a withdrawn permission. `exec_command`
  therefore re-checks authority after exec returns and before `noteExecOwner`, terminating and
  refusing the session instead of publishing it. Its output is not returned either: it ran under an
  authorisation that no longer exists;
- a boolean re-check cannot survive a true→false→true flap, where the setting reads enabled again
  by the time the call returns. Authority is therefore versioned. `mcp/call-context.ts` holds the
  epoch (a leaf module, chosen to avoid a `workspace` ↔ `ownership` import cycle), the kernel stamps
  `caller.uncapturedEpoch` at admission, and `revokeAuthorizedUncaptured` advances the epoch first,
  before it enumerates anything — so a call returning during the revoke itself is already stale.
  The live setting is still checked alongside the epoch, covering the narrow window inside
  `settings:save` where the config is written but the revoke has not run yet.

`workspaceKey()` uses the same `uncapturedAuthorityCurrent` predicate rather than reading the live
config, so a workspace cannot be learned under a retired grant either.

Regression: `test/uncaptured-revoke.test.ts` (3 tests) covers published-session revocation with
captured owners and workspaces proven untouched, the off-during-initial-yield refusal, and the
flap, the last two through the real MCP server over `tools/call` with real child processes. Each
was mutation-checked: removing `uncapturedAuthorityCurrent` from the fence fails the flap test
alone, and disabling the fence entirely fails both in-flight tests.

Files: `src/shared/types.ts`, `src/main/config.ts`, `src/main/mcp/call-context.ts`,
`src/main/mcp/kernel.ts`, `src/main/mcp/tools-core.ts`, `src/main/workspace.ts`,
`src/main/codex/ownership.ts`, `src/main/ipc.ts`, `src/preload/index.ts`, renderer and tests.

### Windows/Linux application update

`src/main/update.ts` uses `electron-updater` 6.8.9 and electron-builder's official GitHub provider
for `totec448-spec/chat-on-steroids`; it does not scrape release pages.

- Supported installed formats: Windows NSIS, Linux AppImage and Linux DEB. macOS, development and
  unknown package types are explicit manual/unsupported states.
- First check is five seconds after startup; subsequent checks are at most every six hours.
- `autoDownload=true`, `autoInstallOnAppQuit=false`, prereleases/downgrades disabled. Install is an
  explicit top-bar action and first tells app shutdown ownership not to hide in the tray.
- Windows ARM64 uses `latest-arm64.yml`; Windows x64 uses `latest.yml`. Linux's provider uses
  `latest-linux[-arm64].yml` and electron-builder's installed `package-type` marker selects the
  actual AppImage/DEB updater.
- Initialization/network/provider failures do not escape startup. The top bar can retry, and
  renderer-visible errors redact release URLs and local cache/install paths.
- A failed install *handoff* is recoverable, which it was not. `installDownloadedUpdate()` published
  `canInstall:false, canCheck:false` and told shutdown ownership to stop hiding in the tray before
  calling `quitAndInstall`; if the handoff failed, the card stayed permanently on
  "Restarting to install…" with both actions dead and `quitting` left true. The failure is usually
  not a throw — electron-updater 6.8.9's `BaseUpdater.install()` catches `doInstall` and calls
  `dispatchError`, and `DebUpdater` does the same for a failed install command — so an explicit
  `installing` flag is tracked and the `error` listener, not only a `catch`, performs the recovery:
  it calls the paired `installFailed` handler that restores `quitting`/window activation and
  publishes a redacted error state. That state is `canInstall:false, canCheck:true` rather than
  both true, because the renderer's chip checks `canInstall` first: leaving it true would make the
  only visible Retry button re-run the same broken cached installer forever instead of
  re-checking. `test/update.test.ts` asserts the click actually reaches `check`, not the flags.
- The renderer receives bounded `AppUpdateStatus` and two named preload methods, never Node or
  generic network authority.
- Release assembly/publish includes the four metadata files and SHA-256 covers them. Package smoke
  requires `app-update.yml` and executes the packaged `electron-updater` dependency.

Files: `src/main/update.ts`, main/IPC/preload/renderer, `electron-builder.yml`, package manifest/
lock, package/release/publish scripts and tests.

Integrity boundary: updater metadata contains SHA-512 checks used by `electron-updater`, and the
candidate publishes SHA-256 checksums. Current packages are publisher-unsigned; checksums are not
claimed as a publisher signature. macOS auto-update remains out of scope until signing and
notarization are real.

### Cross-platform and performance boundaries

- Core remains live on Windows/macOS/Linux x64/ARM64; Desktop discovery/control remains Windows
  only. Stored Desktop choices are masked, not erased, on other OSes.
- The six native release jobs inspect/execute target resources, native Sharp/node-pty/tree-sitter,
  tunnel/ripgrep helpers, extension contents/version, Electron version and installed Linux GUI
  paths. Static cross-building is not treated as native launch proof.
- Session cursors are short durable references with bounded LRU/legacy compatibility rather than
  large opaque blobs the model must transcribe.
- Command handling narrows proven PowerShell 5.1 operator repair, UTF-8 Get-Content decoding,
  bundled-ripgrep binding and benign/partial-search exit explanations. Model output stays at the
  transport-safe fixed budget rather than advertising a larger discarded payload.
- **Regression found and fixed after the first pass:** retiring `max_output_tokens` from the
  `exec_command`/`write_stdin` schemas broke live calls. Those objects are `.strict()`, and ChatGPT
  caches a connector's tool definitions, so every conversation opened against the older schema kept
  sending the key and got `Input validation error: Unrecognized key: "max_output_tokens"` — the
  whole command refused, no output, in chats that had done nothing wrong. Removing a parameter from
  a cached schema is not a local change; it is a break for every caller still holding the old copy.
  The parameter is declared again and inert: its value is ignored, the budget stays fixed at
  `DEFAULT_MAX_OUTPUT_TOKENS`, and `exec_command` returns `MAX_OUTPUT_TOKENS_RETIRED_NOTE` alongside
  its real output so the model stops sending it because it was told, not because its command
  failed. The description is deliberately short: `tools/list` is re-sent every turn and the exec
  schema is held under a discovery-size budget that a verbose retired parameter would blow.
  Proof: `test/exec-output-budget-mcp.test.ts` now asserts the call succeeds, carries the note, and
  still gets the fixed budget; `test/mcp.test.ts` pins the key as present-but-inert rather than
  absent, and its per-tool discovery-size assertion holds.

## Corrections landed in the co-read pass after that review

Every item below was a gap between what this record claimed and what the source did. They are
listed as defects rather than as features because that is what they were.

- **The uncaptured-caller switch did not revoke.** Recorded as "revokes fallback on the next call",
  which is not revocation: live fallback-owned terminals and the fallback workspace outlived the
  decision. Fixed by `revokeAuthorizedUncaptured()` plus the post-yield publication fence, and then
  by the authorisation epoch after a first fix using a live boolean was shown unable to survive a
  true→false→true flap. Covered by `test/uncaptured-revoke.test.ts`.
- **The Goal retry policy did not match the documented one.** `run()` initialised
  `retryable = true` and never cleared it for `decision.action === 'invalid'` or for the
  deterministic bounds failures, so malformed or over-long model output burned all three attempts
  while this record said only transient failures retried. Classification is now explicit and the
  tests pin attempt counts rather than outcomes. A first revision left
  `malformed_stream_record` classified as transport while the adjacent comment called malformed
  results deterministic; the set now covers all five deterministic strings, so code, comment and
  this record agree.
- **`draftOpeningMessage` bypassed the retry loop entirely**, and the extension's single 10 s
  request timeout would have made app-side retries unreachable through the real route even after
  the loop was shared. Both fixed; see the Goal section.
- **The OpenAI tunnel scheduled two retries for one failed generation** and, after the first fix,
  armed the replacement before the old tree finished retiring. Both fixed; see the tunnel section.
- **A failed update install handoff was an unrecoverable dead card**, and the first fix's
  `canInstall:true` recovery state was itself unreachable through the renderer's click logic. Both
  fixed; see the update section.

Two things are worth stating plainly about the process rather than the code. Several of these were
second-order: the first fix for the uncaptured race, the tunnel retry and the updater recovery each
introduced or left a narrower version of the same bug, and each was caught only by re-reading the
patch against the runtime it actually runs on. And the new revocation tests were mutation-checked
before being believed — removing `uncapturedAuthorityCurrent` from the fence fails the flap test
alone, disabling the fence fails both in-flight tests — because a race regression that passes
against a broken build is not evidence.

## The live Compact & Resume run, and the sixth defect it found

The timed run was the point of the built-in `commandLatency()` measurement above, and it did its
job on the first attempt — by failing. Run on 2026-08-28 in a disposable Chrome chat, from the
app's own Activity log:

```text
08:25:25.500  continuation o9pBhLTC durably opened for session 2026-08-28-99dbdf35 in chat 6a914554-…
08:26:03.643  handoff 2026-08-28-b08d467a prepared (4336 characters)
08:26:03.646  bridge: opening a fresh ChatGPT chat for resume:2026-08-28-99dbdf35
08:26:13.904  session started for a ChatGPT conversation (2026-08-28-f2c6333a)
08:26:13.911  session 2026-08-28-f2c6333a named for the resume chat this app opened
08:26:13.914  continuation o9pBhLTC durably abandoned — the replacement chat already belongs to another local session
08:26:13.916  bridge: resume:2026-08-28-99dbdf35 completed with terminal-failure in 9649 ms
```

The browser half is therefore **9,649 ms**, and the log line prints it exactly as designed. But the
outcome is `terminal-failure`, so this is not yet a clean timing: the browser half completed —
ChatGPT opened chat B, took the brief and replied — while the app half abandoned the move. Source
session `2026-08-28-99dbdf35` kept chat A, and B became a separate `origin.kind=resume` session.

**Root cause.** `session/resume-gate.ts` exists precisely to stop this, and its comment claims
current builds prevent it. They did not. The gate was armed correctly, but the recorder honoured it
only for `RESUME_COMMIT_SETTLE_MS = 5_000` and then created the session anyway. Five seconds was
chosen against how long a *commit* takes (milliseconds); what actually has to elapse is everything
in front of the commit — Chrome start, ChatGPT load, content-script boot, redeem, composer
readiness, insertion, send, and the page reporting which chat it landed in. Live, that was 10.27 s.
The recorder gave up 10 ms before the acknowledgement arrived.

**Fix, and what was rejected.** Raising the constant to the gate's own 60 s window would close this
particular race and open a worse one: an unrelated new conversation opened while a resume stalls
would hang for a minute, and a dead opener would globally block recording. The batch is the thing
that can afford to wait, so `deferForResumeCommit()` now answers `/events` and `/correlations` with
`503 resume_commit_pending, retryable` for a conversation this app has never recorded while the
gate is up. The browser retires a journal row only on 2xx, so nothing is dropped, no shadow session
exists for the commit to collide with, and the retry after the gate clears lands in the session
that was moved onto B. The 5 s settle survives only as a courtesy fast path for the few in-process
callers that have no retry to fall back on.

**Regression.** `bridge.test.ts` — *answers an early replacement-chat observation as retryable
instead of shadowing the resume* — drives the real HTTP routes: queue and redeem a resume, post B's
first observation before the acknowledgement, assert `503 resume_commit_pending`, assert no live
and no durable session for B, then acknowledge and assert the continuation commits, the source

The verified tree was frozen as `proof/2.0.3-native-matrix` (`72c521f`) — a snapshot branch, not a

The four red jobs failed identically — `1 failed | 68 passed` files, `3 failed | 1780 passed`
tests, all three in `test/update.test.ts`, none in packaging:

```text
AssertionError: expected { phase: 'unsupported', …(7) } to match object { phase: 'idle', format: 'nsis', …(1) }
AssertionError: expected { phase: 'unsupported', …(7) } to match object { phase: 'ready', …(2) }
Error: No downloaded update is ready to install.
```

**Root cause, and what was *not* changed.** The policy is correct and deliberate: macOS has no
in-app installer until releases are signed and notarized, and a Linux checkout with no `APPIMAGE`
environment and no `package-type` marker is genuinely an unsupported package. The defect was in the
tests, which read the live `process.platform` through `packageFormat()` and so silently inherited
the Windows workstation they were written on. Production policy was left exactly as it is.

**Fix.** `test/update.test.ts` now states the installed package instead of inheriting it:
`installedAs()` pins `process.platform` and stubs `APPIMAGE`, and an `afterEach` hook — not the end
of a test body, which a failed assertion never reaches — restores both. The lifecycle test runs
`it.each` over both formats that have an installer — `nsis` on Windows and
`appimage` on Linux — and the two installer-recovery tests run as the AppImage their failure text
actually comes from. A new `it.each` pins the other half of the same policy from real inputs: on
macOS, and on an unmarked Linux package, the card stays `unsupported` and inert — no provider call,
and the explicit install act refuses. Coverage went up, not down: 6 tests to 9.

**Proof it is portable.** The file was run three times under a simulated host platform
(`process.platform` forced to `darwin`, `linux`, `win32` before the module loads): 9 passed each
time. Mutation-checked by disabling the fixture: 5 of 9 fail on a simulated macOS host and 4 of 9
on Windows — including, on macOS, the exact three the release runners reported.

## Remaining external/native verification before a release-ready verdict

The live browser work is done: the Compact & Resume run above is green end to end on the packaged

  scope for this document, which verifies the implementation rather than the release.
