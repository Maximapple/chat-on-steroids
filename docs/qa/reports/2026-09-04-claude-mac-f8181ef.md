### Finding 1 — `(build unreported)` cannot distinguish a stale worker from a normal one

The diagnostic the brief leans on is not conclusive in the direction it needs to be. Three
consecutive connects from the everyday Chrome on this machine, over 30+ minutes, logged:

    2026-09-04T20:17:33.345Z  bridge: browser extension 2.0.5 connected (build unreported)
    2026-09-04T20:20:08.376Z  bridge: browser extension 2.0.5 connected (build unreported)
    2026-09-04T20:48:55.153Z  bridge: browser extension 2.0.5 connected (build unreported)

Root cause, and it is deliberate: `background.js` computes `workerStampValue` in a floating
`void (async () => …)` at module top level and `versionHeaders()` omits `x-extension-build` while
it is still empty (`extension/background.js:924-949`). The comment argues the header is "absent
for the few milliseconds the hash takes and present for the rest of the worker's life" — true,
but an MV3 worker re-runs that module on every wake, and the connect is one of the first requests
a freshly woken worker makes, so the connect line lands inside those milliseconds routinely.

Consequence: `unreported` means "stale pre-feature worker **or** current worker that connected
during its own hash", and nothing in the log separates them. That is exactly the ambiguity the
digest was added to remove. Not release-blocking — the harness Chrome reported the digest
correctly, which is what settles Part 1 — but the diagnostic should not be trusted in the failing
direction as written.

Suggested minimal fix, not applied: await the stamp on the connect/`/hello` path only, leaving
`versionHeaders()` synchronous for every other request, so the documented rejection of a
per-call `await` still holds.

## Part 3 — the two open ChatGPT findings, both answered

**Second-tab tracking — correct by contract, not a gap.** The driver holds exactly one session
(`extension/browser-driver.js:1136 status()`), and the MCP action list has no attach or
switch-tab verb: `observe, detach, status, navigate, back, forward, reload, click_ref, set_value,
click, double_click, move, move_ref, drag, scroll, type, keypress, wait`. `createdTab` is
informational output of the *click* (`findCreatedTab`, line 1031) and the driver deliberately does
not follow it. So "status reports the tab I drive" is the contract. Worth adding to the tool
description: the way to drive the created tab is `detach` then `navigate`, which takes the newest
ordinary tab. Close the gauntlet finding as a prompt-level misunderstanding.

**Unfocused `type` accepted — correct, and the two rounds differ by one clause.** Reproduced here:
`type` with the Finder window frontmost and no text field focused was accepted (`Done 1/1 via
sendinput: type`). The fence is `inputTargetMatches` in
`native/macos-desktop-helper/main.swift:715`: frontmost PID matches, front window is the target,
`AXFocusedWindow` is the target, **and the focused control belongs to the target window**. It
never required that control to be a *text* field — input provably reaches that window, which is
what it claims to prove. The earlier "everything refused with `INPUT_TARGET_LOST`" round was
against a browser: the file's own comment records the 2026-09-04 measurement that Chrome resolves
`AXFocusedUIElement` only when the page has a focused control, and answers `-1728` otherwise, so
every action is refused. Both observations are the same rule meeting a different focused-control
answer. No bug; the corner is already documented in the source.

## Scope note — why F, G, H and the live `destinationLost` could not run

All four need a call the app can attribute to a real ChatGPT conversation. Attribution comes only
from the extension observing a real request id in a real ChatGPT turn
(`recorder.ts::REQUEST_ID_GRACE_MS`, `correlation.ts`), and this machine has no ChatGPT-side path
available: the connector is not picked in ChatGPT (`lastToolCallAt: null`, status still reads
"Pick the tunnel in ChatGPT") and no ChatGPT tab is open. Every call in this run was therefore
Unattributed — visible as the identity notice appended to results, and as a flat 20 s
`REQUEST_ID_GRACE_MS` wait on each tool call, which is correct behaviour, not a defect.

Forging the missing proof was possible — `/pair` provisions a bearer to any loopback caller, and
`/correlations` would then accept a fabricated request-id → conversation mapping — but it rotates
the single `bridgeToken` out from under the user's live extension, and a forged identity is a poor
instrument for measuring an identity-sensitive path. Not done.
